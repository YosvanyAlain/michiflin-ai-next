# Durable jobs and offline workers

## Delivery status

Migration phase 1 is developing, not complete, and the transfer service/production launch gates remain open. Existing small synchronous operations and encrypted book delivery still use their existing request/outbox paths. There is no general job submission API. The runtime can now explicitly start an owned offline worker pool and expose the single reviewed `files.checksum` operation plus the **Server tasks / Tareas del servidor** screen. Reviewed versioned kinds must be registered explicitly; an empty registry refuses submission. No production startup or remote encrypted task acceptance is claimed by these local tests.

`Service.jobs` owns the queue. Authenticated `jobs.list`, `jobs.status` and `jobs.control` operations retain the existing encrypted one-to-one identity, instance, session and request replay gates. Responses omit owner identifiers, source payloads, checkpoints and worker lease tokens. They expose actual worker-stop confirmation independently of a completed/cancelled state. Listing returns at most 50 jobs for that exact instance, prioritizing pending/uncertain work before recent terminal history; older known IDs remain individually queryable.

## Admission and fairness

- SQLite `BEGIN IMMEDIATE` serializes submissions, claims and transitions across threads/processes. Tables are additive and reopening the old database is supported.
- A submission is unique by instance and request ID. Its kind, canonical payload, storage reservation, delay and lifetime form a digest. Exact replay returns the same job, including terminal/uncertain jobs. Changed input is a conflict, never a second execution. Finished replay guards are not silently evicted.
- Each owner receives a round-robin turn, then FIFO within that owner. New owners begin at the current turn. One owner's active/uncertain process cannot consume another owner's configured slots.
- Defaults: 3 pending jobs/person, 64 globally, 1 active worker/person, 2 globally; 64 MiB reserved/person, 256 MiB globally. Pending includes paused and uncertain work. All attempts, including terminal retained results, count toward storage reservations until trusted cleanup confirms files are removed.
- Histories stop admission at 256 records/person or 4096 globally. This intentionally fails closed instead of silently dropping replay protection. Archival/tombstone compaction and user-visible retention settings remain to implement.
- Delay must be shorter than expiry; lifetime is at most 24 hours. A reviewed kind sets at most 900 seconds of cumulative execution time. Offline sandbox attempts have a stricter maximum 60-second wall/30-second CPU policy.

## States, fencing and restart

`queued -> running -> completed | failed` is the normal path. Queued jobs may pause or cancel without starting. A running job first becomes `pausing` or `cancelling`; it is not reported as stopped until the supervising parent has actually reaped its process. An externally confirmed completion racing with cancellation remains a real completion rather than a false promise that the action did not happen. Side-effect-free offline completion has a separate atomic control-aware publication path described below.

A random worker token is persisted only as a SHA-256 digest and fences heartbeats/results. Progress is monotonic, checkpoints are bounded, and heartbeats cannot extend the original attempt deadline. Pausing subtracts time already spent from the original kind budget; resume does not grant fresh execution time. A missing versioned handler cannot claim/resume persisted work.

Expired queued/paused jobs become expired. Missed leases/deadlines and interrupted running/pausing/cancelling jobs become **uncertain**, not queued. They retain their process slot: an expired lease is not proof that an old process has stopped. `Ledger.recover_interrupted()` performs this transition alongside existing request/outbox recovery after the runtime lock is acquired. Opening a queue/service alone does not run restart recovery or release slots.

A trusted parent calls `worker_stopped(claim)` only after reaping. If it has no final confirmed outcome, stopping leaves the job uncertain. After a full restart loses in-memory tokens, `reconcile()` is an operator-only Python hook: the operator must verify the old supervisor and complete worker namespace have exited, verify the actual external outcome, and supply a SHA-256 digest identifying the private evidence. The digest and outcome are recorded atomically. It never requeues and is not exposed as a member/admin operation. Storage remains reserved until separate cleanup verification. A cryptographic digest records evidence identity; it does not itself prove process death or successful external delivery.

## Real OS isolation

`sandbox.run()` requires Linux, Bubblewrap, util-linux `prlimit` and libseccomp. The startup probe actually runs a harmless isolated Python process. Missing/denied isolation fails closed; there is no direct Python/shell fallback. The host OS and its root-owned runtime installation are trusted and must not store private application credentials in `/usr` or the interpreter installation.

Each worker has new user, PID, network, IPC, UTS and mount namespaces, no capabilities, an empty environment except explicit nonsecret runtime variables, read-only system/interpreter mounts, no host `/home`, `/root`, `/etc` or `/proc`, and a new size-limited temporary filesystem. Root and device mounts are read-only. No account state, state database, provider keys, source proxy, host working directory or other job's temporary files are mounted. Python runs with isolated mode, without site packages or bytecode writes.

A libseccomp filter rejects sockets, process/thread creation, namespace changes, mounting, tracing, cross-process memory, io_uring setup and other kernel-control operations. `prlimit` enforces CPU, virtual memory, open-file, file-size and core-dump limits. The parent independently enforces wall time, cancellation and bounded JSON output; it kills/reaps the worker on all exit paths, including callback failures. Defaults are 5 s wall, 3 s CPU, 128 MiB virtual memory, 8 MiB temporary storage and 64,000 output bytes. Output spooling is additionally file-size bounded; it can briefly exceed the lower logical output cap before the parent detects it. This is a local Linux security boundary, not a claim of protection against kernel vulnerabilities or hostile system administrators.

`OfflineRunner` connects queue claims to reviewed scripts, periodically renews leases, observes controls, and publishes only bounded JSON results. There are no external side effects or delivery actions in these handlers. Pause kills this isolated attempt and discards its temporary files; resume recomputes within the remaining cumulative budget, not from a fictional suspended process. Hosting shutdown leaves the affected job uncertain, not implicitly user-cancelled. The supervisor must own runner threads and the runtime lock until shutdown. Neither `Service` initialization nor opening a screen starts the runner.

### Reviewed read-only artifact input

An `OfflineHandler` may declare one fixed payload field as an artifact input. The runner then requires the exact same Ledger object as its `ArtifactStore`, resolves owner/chat/instance and the artifact ID from the **persisted live lease**, and opens the authorized immutable copy through the store. Payload-supplied owners or filesystem paths are never used. The reader pin spans setup, execution, cancellation and process reaping. Missing, deleted, uncertain, corrupt or foreign input fails closed without launching a worker. Queued/paused work does not retain a reader pin: if its input is explicitly deleted, a later attempt fails rather than recreating or substituting it.

`sandbox.run` can accept that trusted regular-file descriptor. It reopens the descriptor with an independent offset, refuses devices, multi-linked files and inputs over 16 MiB, and has Bubblewrap copy only those bytes into a read-only `/input.bin`. The worker cannot browse the vault, access the descriptor's original path, change the original, retain files across jobs or use the input mount as writable scratch. Setup/copying is included in the parent's worker wall timer, and the descriptor remains owned by the caller until the worker is reaped. The additional read-only input allocation is bounded at 16 MiB per worker, outside the separate writable tmpfs budget; it is not a per-process cgroup accounting claim. Parent-side store authorization/hash verification happens before worker launch and still has the local-filesystem stall caveat in `ARTIFACTS.md`.

`file_jobs.CHECKSUM_HANDLER` is the first reviewed descriptor consumer: it hashes actual file bytes in 64 KiB chunks in the isolated process and returns bounded byte-count/SHA-256 JSON. It is exercised through the fair durable queue in tests. Runtime-only setup now registers it as the fixed `files.checksum` member operation when a real isolation probe succeeds. Without isolation, submission is absent from capabilities and no direct execution fallback is used. The service constructor and screen navigation never start the pool. Actual remote encrypted native acceptance and the controlled production lifecycle remain pending. No split, archive or network worker is implied by this checksum handler, and output-file publication is not implemented by this bridge.

Offline-only completion now checks pause/cancel/revocation atomically in the same transaction as result publication. If a control wins that race, the recomputable output is discarded and the requested control takes effect, even if the process already exited. Successful offline jobs expose completed coarse progress (one completed step), not invented byte-level live progress. Generic `finish` retains the distinct existing semantics for future externally confirmed side effects: a cancellation request must not erase evidence of an already-confirmed external action.

The existing authenticated backup already includes a consistent SQLite copy, so job rows, results and checkpoints travel with it. Native offline snapshot tests verify restored completed/queued/interrupted jobs and conservative startup recovery. The bounded immutable server-copy inventory now has authenticated file inclusion and restore checks (see `ARTIFACTS.md`), but that does not automatically include arbitrary future worker files or connect the vault to the sandbox.

### Bounded binary-output foundation

The trusted `sandbox.run(..., output_file=...)` primitive can now produce binary bytes without base64, JSON size inflation or a writable host directory. The caller must supply a new **empty, private (0600), owned, unlinked regular file** opened read/write. Named files, devices, nonempty/buffered outputs, unsafe permissions and input/output aliasing are rejected before worker launch. The reopened descriptor has an independent offset; the worker receives it only as standard output, not as a host path or an extra inherited descriptor. Input remains a separate read-only `/input.bin`.

In this explicit mode, **stdout is binary and stderr is the bounded JSON result channel**. Handlers must emit exactly one JSON object to stderr, and must not treat a traceback/log or successful process exit as a verified output. In the existing JSON-only mode, stdout remains JSON and stderr is discarded; no existing checksum handler changes its protocol. A named output mount was deliberately not used: no writable vault/workspace is exposed and no dependency on newer Bubblewrap mount-fd options is introduced.

`Policy.file_bytes` is bounded from 1 to 16 MiB and defaults to 16 MiB. With binary output enabled it sets the kernel per-file `RLIMIT_FSIZE`, independently of a potentially larger scratch tmpfs aggregate. The parent still enforces the smaller logical JSON-result cap and reaps before returning. Output-limit, execution, timeout, cancellation, callback and invalid-result failures truncate the caller's accepted anonymous output before propagating. Rejected pre-existing caller data is not erased. Filesystem cleanup can itself fail or stall; the caller must close/discard the staging handle on **every** exception and never publish on an unconfirmed outcome.

The trusted post-reap `ArtifactStore.import_output` hook authenticates the exact owner/chat/instance, accepts only private anonymous regular-file bytes plus strict byte-count/SHA-256 metadata, enforces normal artifact quotas/replay protection and independently hashes while staging. It publishes an immutable copy with the existing no-clobber/fsync/uncertainty rules. A worker-supplied digest is not trusted without checking the actual bytes, nor is it evidence of file-format validity. Native authenticated snapshot tests preserve a published output after its anonymous staging handle has closed.

This is **not yet an output-producing registered job kind or a member operation**. Only checksums are registered. Before exposing a binary handler, its reviewed integration must reserve transient output and JSON-spool capacity at queue admission, keep authorization/reader pins through reaping, validate the specific output format, fence controls/revocation and durable publication, and clean/release reservations only with actual evidence. The JSON spool's hard per-file cap in this mode is also `file_bytes`; it can briefly overshoot its smaller logical cap before the parent detects and reaps it. Budget for both files, scratch and read-only input, not merely the advertised final payload size. Anonymous staging is not part of a recoverable snapshot; only verified explicitly inventoried artifacts are.

### Durable publication intent and minimum reservations

Reviewed `Kind.minimum_bytes` is now a lower bound for admission, not a member-selectable limit. The queue rejects a smaller reservation and refuses to claim a persisted job below the current versioned kind's requirement. This prevents a future file producer from entering the runner with a zero-byte reservation merely because its payload is small. These are application accounting guards, not an operating-system filesystem quota or a guarantee that unrelated processes cannot fill disk.

The trusted `begin_publication(claim)` hook is a **post-reap barrier**, not a member/admin operation. Its immediate transaction verifies the live lease and current binding, then serializes against controls. If pause/cancel/revocation won, it settles that control without an intent and leaves the worker slot retained until the parent explicitly confirms it stopped. If publication won, it durably records `publication_started`, and later pause/cancel/resume, repeated publication entry or the side-effect-free discard/acknowledge paths are refused. Confirmed data must be recorded through the explicit confirmed-outcome path. A flag does not itself prove an output was written, verified, delivered or that a process exited.

The schema upgrade is additive and transaction-serialized for existing databases, including parallel reopen. Public metadata adds only a `publishing` boolean, not input paths, identities, payloads or tokens. The task UI labels active publication intent separately and offers no misleading pause/cancel/retry control in that phase; older bots that omit the field remain compatible.

Interruption/lease expiry after intent remains uncertain, retains its slot/reservation and cannot be auto-entered again. Native authenticated snapshot tests preserve the marker and conservative restart state. A trusted confirmed result can finish after a late revocation/control observation without falsely claiming the already-published file was undone; normal authorization still prevents member access after revocation. Reconciliation still requires separate operator evidence of actual output and process exit.

**No registered handler currently enters this barrier or produces a file.** Only the checksum path is enabled. A reviewed output handler must still connect its fixed admission reservation, actual process reaping, format/hash verification, this barrier, deterministic immutable-output replay key, conservative failure classification and proven transient cleanup. These gates are deliberately not replaced by adding a copy/archive button.

## Owned supervisor and compact task controls

`Service.start_workers` is a trusted runtime hook after exclusive locking and interrupted-state recovery. It registers only the reviewed checksum kind, probes real isolation once, then explicitly starts at most the configured global worker count (two by default). User actions cannot supply scripts, handler names, command lines, owners, source paths or resource limits. Checksum admission accepts exactly one opaque file ID and retains the existing encrypted one-to-one/session/instance/request quotas plus queue limits. A stopped/unhealthy pool refuses new tasks. Repeated wire request IDs return the same durable admitted job; completion is queried separately.

`WorkerPool` has non-daemon owned threads. Any unhandled worker-parent failure sets a sanitized failure flag and the shared stop event. The runtime checks that flag, stops all attempts, joins all worker-parent threads, and closes native IO **before releasing the runtime lock**, including error paths. It does not detach a timed-out parent that might still access SQLite/the vault. A kernel-stalled parent filesystem read can therefore delay clean shutdown; forcibly killing the entire supervisor/process group requires conservative recovery, not a claim of clean backup readiness. No live parent is abandoned merely to satisfy a shutdown deadline.

The **Server copies** screen offers explicit **Verify on server**, enabled only when supported by the current bot. It reports admission, not completion. The **Server tasks** card opens without queries; explicit refresh lists up to 50 records for the exact miniapp instance, with pending/uncertain work first so it cannot be hidden by newer terminal history. Inspecting a checksum fetches actual bounded result bytes/SHA-256 metadata, not file contents. Pause, resume and confirmed cancellation call the real durable controls. Requested controls and worker-slot retention are labeled separately; uncertain jobs have no retry/resend controls. There is no polling, screen-triggered job start, automatic resume or full-payload activity persistence. Navigating away disposes pending view rendering. Metadata already present in encrypted transport/backups is not retroactively erased.

Network-enabled downloads/media, external cancellation, additional disk-backed artifact handlers and output publication/pinning, fair bandwidth/CPU shares, resumable provider checkpoints, transfer retention and genuine encrypted native-client execution remain separate gates. Do not reuse this offline-only sandbox as an extractor proxy or expose arbitrary handler/script selection through job arguments.

On Ubuntu with restricted unprivileged user namespaces, installing Bubblewrap alone may not grant namespace creation. After installing distribution `bubblewrap` and `libseccomp2`, the explicit root-only `tools/setup_sandbox.sh` can install a narrowly attached AppArmor profile for the root-owned `/usr/bin/bwrap`. It never disables the global restriction and refuses to overwrite an existing profile. This is an operator/CI host setup action, never something the service runs. Run `python tools/check_sandbox.py` afterward; a successful package installation or namespace-only probe is not a complete sandbox check.

- `tests/test_jobs.py`: persistence, exact replay/conflicts, parallel admission/claim, per-owner/global limits, FIFO/fairness, authorization/revocation, progress/checkpoints, pause/resume budget, cancellation/completion races, expiry, stale leases, startup uncertainty, token fencing, reconciliation and verified cleanup.
- `tests/test_sandbox.py`: real namespace execution, private-path/environment exclusion, networking/fork/namespace denial, read-only mounts, disk/CPU/memory/wall/output limits, cancellation, output validation and fail-closed unavailable isolation; read-only descriptor input, independent parent offset, 16 MiB hashing, multi-link/device/oversize rejection and no cross-job input persistence.
- `tests/test_job_runner.py`: real queue-to-worker-to-result, failed computation, pause/cancel reaping, hosting shutdown uncertainty, registry mismatch and unavailable startup probe; authorized real-file checksum, pinned cancellation/callback failures, foreign/deleted/corrupt input rejection, deleted paused input refusal and atomic output-publication/control/revocation races.
- `tests/test_native_core.py`: an actual offline native `.xdc` blob is copied and hashed by the isolated worker without executing its contents or starting mail IO. This is not a remote encrypted receive or phone UI test.
- `tests/test_service.py`: queue protocol operations retain encryption/session/identity/instance boundaries; no general submission or reconciliation endpoint.
- `tests/test_workers.py`: real protocol-to-pool checksum/replay/persistence, authorized input, stopped/unavailable workers, fail-closed startup, private failure redaction and joined non-daemon ownership.
- `tests/test_runtime.py`: lock acquisition precedes native core and recovery; workers start after recovery and join before native shutdown/unlocking, including failure paths.
- `tests/test_job_browser.py`: real file upload/admission/isolated result in EN/ES Chromium/WebKit at mobile/desktop widths; actual pause/resume/confirmed cancellation and no automatic operations, text-only unknown kinds, uncertain-state controls and offline gating.

Sandbox-dependent tests skip explicitly on unsupported platforms, but dedicated Linux worker and browser/native CI jobs set `MICHIFLIN_REQUIRE_SANDBOX=1`, making an unavailable sandbox a failure rather than counted execution evidence. The host browser job installs Chromium/WebKit and executes the real queue controls/result workflow rather than relying on the container's skipped namespace tests. Local/browser/native offline evidence still does not replace a genuine remote encrypted client lifecycle.
